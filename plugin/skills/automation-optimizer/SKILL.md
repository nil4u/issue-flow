# 自动化优化分析

本 Skill 用于分析来源 Issue 在指定阶段的真实执行过程，找出 Agent 为什么没有一次完成任务，以及怎样让后续同类任务减少可避免的人工介入。

这里的“一次完成”是指：Agent 在该阶段的首次 Task 中完成阶段要求的产物、操作和验证，不再需要人补充本可提前获得的信息、纠正执行方法或要求补做遗漏步骤。真实产品选择、业务判断和不可预知的外部变化不属于应消除的人工介入。

当前任务应来自带 `type::optimization` 的优化 Issue。来源 Issue、所有待优化阶段及其 Turns 由该 Issue 正文提供。优化 Issue 永远使用 Markdown Plan，不使用 Decision 或 Visual Plan。

## 获取完整执行上下文

分析前必须明确：

- 来源 Issue 编号；
- 一个或多个目标阶段：`triage`、`plan`、`build`、`review`。

执行一次上下文脚本，获取来源 Issue 整个生命周期的 Task：

```bash
node .agentrix/plugins/issue-flow/skills/automation-optimizer/scripts/task-context.cjs \
  --issue <来源 Issue 编号>
```

脚本会输出一个临时索引文件和 `triage`、`plan`、`build`、`review` 四个阶段文件的路径。每个阶段文件包含该阶段全部 Task 和全部 `events`。不要筛选事件类型，不要把这些临时文件放入仓库或提交到 Git。

先读取索引，再读取优化 Issue 正文列出的目标阶段文件，完成目标阶段 Task Facet 后，如果判断该阶段的信息不足以分析问题，需要用上下游阶段理解问题来源或传播过程，再读取其他阶段来理解整个流转过程。

如果某个阶段没有返回 Task、事件不完整，或者来源 Issue 与阶段无法确定，不得猜测根因。应在 Markdown Plan 中明确缺少的数据及其影响。

## 分析方法

### 1. 定义首次完成标准

先根据 TaskEvent 中保存的实际 Task Message、来源 Issue、仓库内容和已有项目约定，写清该阶段首次 Task 应完成什么：

- 应生成或修改的产物；
- 应执行的关键操作；
- 应完成的检查或验证；
- 什么状态代表该阶段已经正确结束。

不要用后续人工评论倒推一个初始阶段不可能知道的要求。

### 2. 分别还原各阶段 Task

一个待优化阶段通常对应一个 Task。对 Issue 正文列出的每个目标阶段，读取对应阶段文件，按 `sequence` 分别还原 Task 的完整执行顺序，识别：

- 初始输入；
- Agent 的理解、操作和验证；
- 工具结果和失败；
- Agent 首次交付的结果；
- 后续人工补充或纠正；
- 修改后的最终结果。

先为每个阶段形成独立 Task Facet，保留该阶段自己的 `taskId`、事件证据、首次完成标准和人工介入。不得在这一步提前把不同阶段的问题混在一起。

### 3. 分析每次后续人工介入

对初始输入之后的每次 `human_input` 回答：

1. 人具体补充、否定或纠正了什么？
2. 首次 Task 的结果与最终正确结果差在哪里？
3. 正确信息在首次执行前是否已经存在于 Issue、仓库、Prompt 或 `.issue-flow/instructions.md`？
4. 应在 `.issue-flow/instructions.md` 中新增或改写哪条项目说明，才能预防、检测、规避或正确处理这个问题？
5. 该说明存在时，这次介入是否仍会发生？
6. 该改动是否适用于后续同类任务，而不是当前 Issue 的一次性偏好？

### 4. 判断根因类型

使用最接近的根因类型，避免“理解不足”“提高准确率”等抽象结论：

- **缺少上下文**：必要信息在首次执行前确实不存在。
- **已有上下文未使用**：信息已存在，但 Agent 没有读取或应用。
- **需求理解错误**：目标、边界或约束被错误解释。
- **执行路径错误**：目标正确，但选择了错误方法。
- **执行不完整**：遗漏要求、操作、产物或交付步骤。
- **缺少验证**：问题本可通过确定性检查提前发现。
- **工具或流程缺口**：现有脚本、CLI、Provider 或工作流无法稳定完成。
- **基础设施失败**：权限、网络、服务或运行环境失败。
- **必要人工决策**：必须保留的真实产品或业务选择。

### 5. 判断是否需要读取其他阶段

完成目标阶段 Task Facet 后，先判断当前证据能否独立解释人工介入和根因。出现以下任一情况时，再读取相关上游或下游阶段文件：

- 当前阶段使用了前一阶段生成的分类、方案、代码或审阅结论，而问题可能来自该输入；
- 人工纠正明确提到前一阶段遗漏、错误理解或错误产物；
- 当前阶段只能看到问题表现，无法从本阶段事件确定问题最初在哪里产生；
- 需要确认同一约定是否在其他阶段被重复补充或再次违反；
- 候选项目说明会影响其他阶段，需要检查是否造成重复规则或执行冲突；
- 优化 Issue 本身列出了多个问题阶段，需要判断它们是否属于同一因果链。

如果目标阶段的事件已经足以证明根因、优化位置和验证方式，不要为了“完整”而读取无关阶段。

### 6. 按需进行跨阶段联合分析

读取其他阶段后，按 `triage → plan → build → review` 串联相关 Task Facet，分析问题如何沿 Issue 生命周期传播：

- 前一阶段遗漏或错误的信息，是否导致后一阶段采用错误输入？
- 后一阶段的人工纠正，是该阶段自身缺口，还是前一阶段问题的延迟暴露？
- 同一项目约定是否在多个阶段被重复补充？
- 哪个阶段是最早可以稳定阻止问题发生的位置？
- 除最早预防点外，是否需要在项目说明中要求后续阶段执行已有检查作为防线？

联合分析不是简单合并相似文字。一个根因可以引用多个阶段的 `taskId + sequence`，说明它在不同阶段的表现和传播；彼此独立的根因仍应分开。最终优化应在 `.issue-flow/instructions.md` 中形成最小且可复用的项目说明，优先阻止问题最早发生，避免为同一因果链重复增加规则。

是否联合分析由证据决定，不由目标阶段数量机械决定。一个目标阶段的问题也可能需要追溯上游；多个目标阶段也可能是彼此独立的问题。

### 7. 形成项目说明改动

所有可实施的优化都必须修改 `.issue-flow/instructions.md`。Issue Flow 会把该文件直接嵌入各阶段任务 Prompt；它是本流程唯一允许的优化落点。其内容与默认阶段 Prompt、公共 Skill 或其他项目执行说明冲突时，应优先遵循 `.issue-flow/instructions.md`。

把根因转换成 Agent 可以稳定执行的项目说明：

- 写明适用阶段和触发条件；
- 写明必须读取、判断、执行或验证的动作；
- 写明完成标准和禁止行为；
- 尽量引用仓库中稳定存在的文件、命令或约定；
- 优先修改已有说明，避免重复增加表达相同含义的规则。

不得通过本优化流程直接修改阶段 Prompt、公共 Skill、checker、validation、工作流、脚本、CLI、Provider 或其他工具。但分析认为这些部分存在问题时，仍必须把当前项目可执行的预防、检测、规避、降级或失败处理要求写入 `.issue-flow/instructions.md`：

- Prompt、公共 Skill 或流程不适合当前项目：写明本项目应采用的判断、顺序、边界和完成标准，由项目说明覆盖默认行为；
- checker、validation、脚本、CLI、Provider 或工具能力不足：写明使用前检查、替代路径、失败识别、停止条件和人工升级方式；
- 基础设施不稳定：写明如何识别基础设施失败、保留证据、避免错误修改业务代码，以及何时重试或转人工；
- 真实业务选择：不得替用户作决定，应写明识别条件、必须向用户确认的信息，以及得到答复前禁止继续的动作。

项目说明不得虚构不存在的工具能力，也不得声称已经修复底层系统问题。若项目级规则只能降低影响而不能消除根因，应在 Plan 中明确底层限制，同时仍把 Agent 必须执行的处理规则写入 `.issue-flow/instructions.md`。

不要因为一句人工评论就新增说明。先确认它代表稳定、可复用的项目要求，而不是当前 Issue 的一次性偏好。

## 在 Markdown Plan 中记录 Task Facet

Task Facet 是分析结果的一部分，直接写入运行时指定的 Markdown Plan output file，不创建额外 JSON 或独立分析产物。

每个目标阶段至少记录：

- 阶段与 `taskId`；
- 首次完成标准；
- 首次实际结果；
- 关键人工介入及其 `sequence`；
- 最终正确结果；
- 首次结果与最终结果的差异；
- 根因类型与根因；
- 可避免或必须保留的判断；
- 拟修改的 `.issue-flow/instructions.md` 内容与反事实判断。

每个目标阶段写一个 Task Facet。按需读取的其他阶段只记录与根因判断有关的证据；如果进行了跨阶段分析，再增加跨阶段因果链，不能用一份混合摘要替代各阶段证据。

## Markdown Plan 要求

分析结果必须进入当前优化 Issue 的正常 Markdown Plan 审阅流程，不得在 Plan 获批前直接实施。Plan 至少包含：

1. **优化目标与首次完成标准**：来源 Issue、目标阶段及该阶段一次完成的判断标准。
2. **Task Facet**：保留影响结论的关键事件和证据，不复制完整会话。
3. **跨阶段因果链**：需要读取其他阶段时，说明为什么需要扩展分析、问题从哪里产生、如何传播、在哪里暴露，以及最早可预防点。
4. **证据与根因**：逐项引用 `taskId` 和 `sequence`，区分表象、直接原因和可复用系统缺口。
5. **优化改动**：给出 `.issue-flow/instructions.md` 的具体新增或修改内容，以及它要求 Agent 改变的行为。
6. **反事实验证**：说明为什么该改动能够避免对应阶段以及后续阶段的人工介入。
7. **验证方法**：给出能证明同类任务首次执行即可完成的复现场景或检查方式。
8. **保留的人工决策**：列出不能也不应该自动化的部分。

优先形成少量高价值改动。不要重复建议，也不要输出没有明确落点的“加强理解”“提高准确率”等抽象结论。

## 硬性约束

- 不得只根据 Turns 数量推断根因。
- 不得忽略非消息类型的 TaskEvent。
- 不得在没有事件证据时补写执行过程。
- 不得把完整会话、敏感数据或临时上下文文件提交到仓库。
- 所有可实施优化只能修改 `.issue-flow/instructions.md`。
- 不得直接修改阶段 Prompt、公共 Skill、checker、validation、工作流、脚本、CLI、Provider 或其他工具；发现相关问题时，必须把项目级覆盖、检查、规避或失败处理规则写入 `.issue-flow/instructions.md`。
- 不得在优化 Plan 获批前实施优化改动。
